1 · Deepen the character store behind a record-lifecycle seam

Strong dependency: local-substitutable

after

App.svelte — view state only

one record interface: list · save · remove · removeMany · backfill

id generation · createdAt policy

db.ts — transaction adapter (kept)
problem
App.svelte is both the root view and the record-lifecycle module: it reaches across the db.ts seam with five per-record verbs while owning the createdAt, re-read-guard, and backfill invariants, so persistence behaviour can only be tested by mounting the whole root.
solution
Put a characterStore module at that seam: a small record interface hides connection state, id generation, the createdAt policy, the re-read guard, and the backfill loop, with db.ts kept as the internal transaction adapter.
deletion test
Passes. Today the policy already exists inline in App; the store concentrates it. db.ts must stay — deleting it would scatter the transaction plumbing instead.

wins

  • locality: createdAt rule has one home
  • leverage: App keeps only view state
  • backfill guard tested without mounting App
  • five null-checks leave the view
  • db.ts stays the transaction adapter
  • save / delete / backfill share one seam

problem
download.ts carries two concerns at once — pure data-URL and filename rules that node tests cover well, and a browser rendering mechanism that duplicates image.ts's Image load dance and whose canvas path no test crosses.
solution
Deepen image.ts into the one module for browser-image operations (load, measure, convert to a PNG blob) and leave download.ts the parsing, filename, and download gesture; the rendering mechanism sits behind a seam with a test double.
deletion test
Passes. Deleting image.ts would send measureImage back to its two callers and leave convertToPng duplicated; the mechanism belongs in one module.

  • pure download rules stay node-testable
  • download.ts interface narrows
  • untested mechanism gains an adapter
  • measure and convert share one home

4 · Deepen the feedback seam (notice + confirmation policy)

Speculative dependency: in-process

src/App.svelte:18–45, 105–121, 139, 171 · src/components/ConfirmDialog.svelte · tests/app.test.ts

before

after

sequenceDiagram

  participant F as feedback
  participant D as ConfirmDialog (view)
  C->>F: confirm(message)
  F->>D: open
  D->>F: decision(ok)
  Note over F: focus capture + restore live here
  F->>C: boolean

The promise cycle and focus rules move behind one small interface; App renders, it does not decide.

problem
The notice state and the confirm promise handshake — focus capture, resolution, focus restore — live as closures in the root module, so the policy has no module and its only test surface is the full DOM.
solution
Deepen a feedback module that owns notice state and the confirm request/decision cycle behind a small interface; App.svelte renders the notice and the ConfirmDialog view from that state.
deletion test
Passes, narrow. The policy would reappear in App with no other home. Leverage is future-facing until a second dialog or notice site exists, so revisit when the next one lands.

wins

  • locality: promise handshake, one home
  • focus capture and restore stay put
  • App renders, does not decide
  • second dialog: zero copied handshake
  • notice rule testable without mounting App

Deliberately deep — leave alone

These already earn their keep; the deletion test would scatter real complexity:

  • db.ts — transaction adapter; abort handling is real behaviour, not plumbing.
  • download.ts parse + filename rules — pure, deep, node-testable.
  • Lightbox.svelte — single teardown path through the close event; a documented sharp edge.
  • MasonryGrid.svelte — CSS-column layout and animation gating; pinned by designMasonry.md.
  • CharacterForm.svelte — draft, measurement, and validation behind three props.
  • gallery-utils.ts — pure rules; two callers for the aspect helper, and the repo convention keeps logic out of modules with markup.

top recommendation

Deepen the character store first

It carries the highest-consequence behaviour — the createdAt rule, the re-read guard, and the backfill loop all exist because stale writes caused data loss before — yet it has the heaviest test surface today: a whole-root mount behind fake IndexedDB, fake Image, and FileReader. Moving it behind a record interface concentrates the invariants and lets the suite cross a smaller seam.
